# 실행 및 검증

## 공통 기반

- 작업 브랜치: `feature/groups-settlement`. 커밋·push하지 않습니다.
- 루트 npm workspace와 공통 `package-lock.json`을 사용합니다. 별도 lockfile을 만들지 않습니다.
- Node.js 22 이상 (권장: 24 LTS). `npm ci`로 고정 버전을 설치합니다.
- Next.js·React·Supabase JS, 검증용 TypeScript·tsx·PGlite를 추가했습니다.
- 로그인 화면·회원가입·앨범·실제 송금은 이번 구현 범위에 없습니다.

## Supabase 준비

1. 두 개발자가 사용할 Supabase 개발 프로젝트를 정합니다.
2. SQL Editor에서 `supabase/migrations/20261102000100_groups_settlement.sql`을 한 번 실행합니다. 이미 적용한 DB에 반복 실행하지 않습니다. 동명 테이블이 있다면 먼저 스키마를 비교합니다.
3. 마이그레이션은 네 공개 테이블, 비공개 초대 테이블, RLS, RPC를 생성합니다. `supabase_realtime` publication이 있으면 `groups`를 추가합니다.
4. Dashboard Database → Replication에서 `supabase_realtime`에 `public.groups`가 포함되는지 확인합니다. 없다면 Realtime을 활성화하고 `groups`를 추가합니다.
5. `apps/web/.env.example`을 `apps/web/.env.local`로 복사합니다. 프로젝트 URL과 publishable key를 입력합니다. service_role/secret key를 넣지 않습니다.
6. 팀원의 `/login` 화면이 공통 `getSupabase()`로 실제 로그인하도록 연결합니다. 그룹 기능은 `useAuth()`의 실제 사용자만 사용합니다.
7. 루트에서 `npm run dev`. http://localhost:3000 접속.

환경변수 없이도 설정 안내 화면을 볼 수 있습니다. 환경변수를 바꾸면 서버를 재시작합니다. 브라우저용 키는 공개 가능한 키이며 접근 권한은 DB RLS와 RPC로 통제합니다.

## 팀원 통합 순서

1. 공통 프로젝트 설정과 lockfile을 먼저 공유합니다.
2. 로그인 담당자는 `shared/supabase.ts`의 단일 인스턴스를 재사용합니다. 인증 모듈이 이미 있다면 `shared/auth.ts`를 해당 모듈에 연결하되 `{ user, loading, error }` 계약을 유지합니다.
3. 로그인 후 `/`로 이동합니다. 로그아웃·세션 만료 시 그룹 화면은 언마운트됩니다.
4. 앨범 마이그레이션은 그룹 스키마 이후 적용하며 `groups.id`와 `group_members` 관계를 재사용합니다.

## 자동 검증

```sh
npm test
npm run typecheck
npm run build
```

외부 Supabase 연결 없이 실행합니다. 정산 계산 테스트와 임베디드 PostgreSQL(PGlite)에서 실제 마이그레이션을 실행하는 DB 테스트입니다. 테스트용 `auth.users`, `auth.uid()`, anon/authenticated 역할로 권한을 재현합니다.

- 균등 분담 잔액·미참여자 제외·송금 후 잔액 0
- 빈 그룹·단독 결제·불일치 분담과 200개 금액 조합
- 익명·그룹 외 접근·직접 쓰기·초대 코드 접근 차단
- 중복 가입 방지·그룹 간 격리·작성자 외 변경 차단
- 오래된 버전 수정·삭제 충돌과 실패 시 롤백
- 스냅샷 조회·삭제 시 분담 내역 연쇄 삭제

호스팅 Supabase Auth, WebSocket Realtime, 실제 복수 연결 행 잠금은 이 테스트의 검증 대상에 포함되지 않습니다. 아래 통합 검증이 필요합니다.

## 두 계정 수동 검증

서로 다른 브라우저 프로필 또는 일반 창과 시크릿 창에서 A·B 계정으로 로그인합니다. 같은 Supabase 프로젝트를 사용해야 합니다.

1. **초대·권한**: A가 그룹을 생성합니다. B 목록에는 나타나지 않아야 합니다. A의 생성자 전용 초대 코드를 B가 입력해 참여합니다. 재참여해도 구성원은 두 명입니다.
2. **공유**: A가 10,001원 결제를 A·B 분담으로 등록합니다. B 화면에 수동 새로고침 없이 나타나야 합니다. 부담액 합은 10,001원이며 UUID가 앞선 사람이 5,001원입니다.
3. **작성자 권한**: B에게 A 결제의 수정·삭제 버튼이 없어야 합니다. A가 결제자 B로 등록해도 수정 권한은 작성자 A에게 있습니다.
4. **보존**: 브라우저를 종료하고 다시 로그인합니다. 그룹·여행·결제·정산이 남아 있어야 합니다.
5. **동시 수정**: 같은 작성자 A로 창 두 개에서 동일 결제를 편집합니다. 첫 창 저장 후 두 번째 창 저장은 충돌 안내가 나와야 합니다. 입력값은 유지되며 편집 취소 후 최신 데이터를 다시 엽니다. 오래된 버전 삭제도 거절되어야 합니다.
6. **삭제 공유**: A가 결제를 삭제하면 B 목록과 정산에서도 사라져야 합니다. 삭제 이벤트 대신 그룹 version UPDATE로 재조회합니다.
7. **연결 복구**: B를 오프라인으로 바꾸고 A가 결제를 추가합니다. B가 온라인으로 복귀하거나 창에 다시 포커스하면 최신 내역이 조회되어야 합니다. 수동 새로고침도 확인합니다.
8. **일정**: 생성자 A만 여행 설정을 변경합니다. 시작일보다 빠른 종료일은 DB가 거부해야 합니다.
9. **정산**: 미참여자를 제외한 결제와 결제자 자신을 제외한 결제를 추가합니다. 총 결제액과 총 부담액이 같고 송금 적용 후 모두 잔액 0인지 확인합니다.

그룹 외 접근은 자동 DB 테스트로 검증하며 실제 Supabase에서도 참여 전 B의 JWT로 네 테이블을 조회할 때 빈 결과, 직접 쓰기 시 permission denied가 반환되는지 확인합니다. 계정 JWT·비밀 키는 문서·로그·저장소에 남기지 않습니다.

## 이번 작업에서 확인한 결과

자동 테스트 13개, TypeScript 검사, 프로덕션 빌드, 로컬 HTTP 200 및 설정 안내 HTML 렌더링을 확인했습니다. 브라우저 상호작용 테스트는 수행하지 않았습니다.

## 현재 검증 한계

실제 Supabase 설정과 로그인 UI가 제공되지 않아 호스팅 마이그레이션 적용, 두 계정 브라우저 통합, Realtime 연결은 수행하지 않았습니다. 배포하지 않았습니다.
